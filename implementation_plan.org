** DONE Nest locations and actors as a many-to-many relationship, not a strict tree
E.g. a shared resource nested under two different composites at once.

** DONE A way to actually establish nesting from the UI
Two ways: the properties panel lists an element's current containers
(with a way to remove each) and a dropdown to add another; dragging a
box so its center ends up inside another box's bounds nests it there (in
the smallest overlapping candidate, if several), while dragging it back
out un-nests it (view display only — see below). Both routes go through
the same model validation (no self-containment, no cycles); an invalid
drag-nest is silently skipped rather than erroring.

** DONE A container visually shows its nested content on the canvas
A container with children present in the same view is drawn as a box
auto-fit around them, with its label moved to the top-left corner so it
doesn't sit on the content.

** DONE Drag a container and have its nested content move along with it

** DONE Distinguish world-model containment from per-view display of nesting
Containment (=Element.parents=) is a fact of the model, shared across
every view. Whether an element is /displayed/ nested is a separate,
per-view choice (=View.nestedUnder=) dependent on the model fact but not
required to match it everywhere. Dragging a box into another establishes
containment in *both* the model and this view's display; dragging it
back out only changes this view's display — the model relationship (and
its appearance in every other view, and in the tree) stays untouched.

Known v1 limitation: an element nested in *two* containers that are both
in the same view still renders as a single box at one position, and
*both* containers auto-fit to include that one location, rather than the
element being drawn once per container. Full "draw once per occurrence"
needs the instance-based view schema (see the open item below).

* Milestone B — Petri nets

** DONE Create places, transitions, and arcs, laid out manually like block diagrams (primitive)
=Place=/=Transition= element types; palette buttons shown when the
active view's =diagramType= is =petri=; "+ View" gained a diagram-type
select. Arcs are directed, carry a weight (default 1, shown as a label
only when != 1), drawn via the shared =FmcModel.arcs=/=addArc= mechanism
(see Milestone C below) rather than a Petri-specific one. Not yet built:
NOP transitions, swimlanes, multi-token/infinite-capacity place styling,
recursion elements, the standard-construct stencils tracked separately
under Milestone A's visualization-guidance items — all deliberately out
of scope for this pass per "primitive support is okay for now".

Reference measurements from a screenshot the user analyzed (em units,
text height = 1.0em as the reference): place diameter ~1.33em; start-
place's filled inner circle ~0.6-0.67em (used for the isStart marker
below); transition box height ~2.4em, width ~4.5em; a NOP-transition bar
~0.67em tall, ~12.0em wide. The NOP-bar dimensions are noted here for
whenever that element gets built; the other two ratios are now both
applied -- see the isStart entry below for the inner circle, and the
default transition size (=palette.gjs='s =addTransition=) for the
place/transition proportions: anchored to the place's existing 60px
diameter (scale ~45.1px/em), the ratios give a transition ~108x203px,
rounded to a cleaner 200x110 -- noticeably larger than the generic
120x60 default every other block-diagram element still uses, since a
transition genuinely reads bigger next to a place in the real notation.
Only affects newly-created transitions; existing diagrams keep whatever
box size they were saved with.

Follow-up fix: a Petri arc almost always exits its source's bottom
(south) and enters its target's top (north), perpendicular to that edge,
via a dedicated =verticalArcPath= rather than the generic shortest-route
=orthogonalPath= (which ER arcs still use, since ER has no fixed reading
direction). Two motivations: FMC's standard Petri net flow is top-to-
bottom, and a naive single-bend route could (a) draw two opposite-
direction arcs between the same pair as one perfectly overlapping line
with an arrowhead at each end — reading as a forbidden bidirectional
edge — and (b) cut straight through a box when the target isn't below
the source.

Refined further for the loop-back case (a transition beside, not above/
below, a place -- the common shape of a self-loop's return arc): instead
of forcing the due-south exit to loop all the way around, the whole
detour routes *above* both boxes, so both ends leave/arrive diagonally
(north-west/north-east, whichever faces the other box) via a short 45°
stub right at the shape's own boundary, then bend onto ordinary
horizontal/vertical routing for the transit between them -- only that
stub is a free-angle segment, never the whole path, and it's still the
particular case, not the default. For a place (drawn as a circle via
=buildShape='s =cornerRadius= trick), the stub's anchor point is the
actual point on the circle at that 45° angle, not the invisible bounding
box's corner -- =diagonalBoundaryPoint= handles both circular and
rectangular shapes with one formula.

Also widened the diagonal stub (16px -> 28px) so canvas =arcTo='s
rounding has enough room to render the *same* corner radius at a
diagonal-to-orthogonal bend as it already does at a plain
orthogonal-to-orthogonal one -- =arcTo= silently shrinks the radius it
draws when the adjacent segment is too short to fit it.

Corrected again: an intermediate version made *both* ends leave/arrive
via a top corner (reasoning that since the transit routes above both
boxes, a bottom entry would force a loop-under). That reintroduced
exactly the bidirectional-overlap bug this whole =verticalArcPath=
exists to prevent -- for a reciprocal pair of arcs between the same two
nodes (A->B and B->A), the corner-selection formula only depends on
which side the *other* box is on, not on which arc is being drawn, so
both arcs landed on the identical top corner of each box and traced the
same line. A second attempt fixed the overlap (source always exits top,
target always enters bottom) but reintroduced real box-crossings for
some layouts and, per direct user feedback tracing a concrete example,
attached the arc to a *corner* on both ends when only one of them (the
place) should ever get diagonal treatment at all.

Corrected a third time, now matching a traced example precisely: a
Petri arc is always place<->transition (the bipartite rule), so exactly
one endpoint is circular. Only that endpoint (the place) gets the
diagonal "leave/arrive on its own circle" corner; the transition always
keeps the plain south(if source)/north(if target) center port the
forward case already uses -- a rectangle's edge midpoint needs no corner
cut. The place's diagonal side (top when it's this arc's source, bottom
when it's the target) always matches the transition's plain port for
the same role, so both ends of one arc land on the same side (above both
boxes, or below both) -- and a reciprocal arc, which swaps source and
target, swaps which end is the place and therefore swaps top<->bottom
too, so the pair never coincides. Two shapes now exist side by side:
when the two boxes are genuinely beside each other (disjoint x-ranges),
this short diagonal-corner/straight-port route applies directly; when
their x-ranges overlap (a reversed arc along a shared column, not really
"beside"), a short corner-cut can't stay clear of both boxes, so it falls
back to the original plain-ports, route-around-via-a-west-lane shape
that predates any of the diagonal work.

Fixed a precision bug in the beside case, caught by tracing an actual
example by hand: the transition end was given its own short vertical
"bend" (via =ARC_ROUTE_MARGIN=), and the shared lane was the min/max of
*both* bends -- but that margin (20px) almost never lined up exactly with
the diagonal stub's own height (28px, measured from a different anchor
point), leaving a near-zero-length leftover segment between the two.
Visually that read as the diagonal overshooting into a spurious, almost
invisible vertical hop before snapping back to horizontal instead of a
clean 45°-to-horizontal bend, and the degenerate segment gave canvas
=arcTo= an undefined direction to round against at the *next* corner too,
so a turn several segments later rendered as a sharp point instead of
curved. Fixed by dropping the straight end's own bend entirely -- since
only the circular end ever needs a detour, the lane is simply that
diagonal stub's own height (only nudged further out if the straight
box's own edge would otherwise stick past it), and the straight end
connects to that lane directly with a single plain segment. Down to
exactly 4 points now (diagonal stub, one bend onto the lane, one bend
into the straight port) instead of 6.

Fixed a second bug in the *forward* case, also caught by tracing a
hand-provided example ("Reg test 3"): a plumb-line shortcut had just been
added there too (drop a straight vertical line instead of forcing the
entry to the target's own center, whenever the source's exit x already
lands safely on the target's edge) -- but the first version applied it
unconditionally, including when the *target* was a place. A place's only
valid attachment point is its own circle pole (center-x); landing
anywhere else along its bounding box's flat top edge doesn't read as
"arriving at the circle" at all, corner margin or not. Fixed by treating
a circular end's own center as non-negotiable and only ever letting a
*rectangular* end's attachment point shift to meet the other side --
when the source is a transition and the target a place, it's the
transition's exit that shifts to line up with the place's fixed pole
(not the reverse), still only when that shift lands safely inside the
transition's own edge.

Fixed a third bug in the loop-back branch, again caught by a
hand-provided example ("Reg test 4"): the "genuinely beside" diagonal
shape assumes the diagonal stub's fixed 28px reach is enough to clear
the far box's near edge -- true when there's a comfortable horizontal
gap between the two boxes, but not when they're pushed flush against
each other (a real, traced case: a place and a transition with the
place's right edge exactly meeting the transition's left edge, zero
gap). The stub landed *inside* the far box, and the connecting segment
cut straight through it. Fixed by measuring the actual gap between the
two x-ranges and only taking the diagonal shape when it's at least
=ARC_DIAGONAL_STUB= wide; anything narrower (including overlapping
ranges, the case this check replaces) falls back to the safe
route-around-via-a-west-lane shape, which stays clear of both boxes
regardless of how tightly they're packed.

Fixed a fourth bug, and a fifth: after the =xGap= fix above, a further
hand-provided example ("Reg test 5") found that the diagonal shape can
still cut through the straight box even *with* a sufficient horizontal
gap, if the two boxes' vertical offset is large enough that the
diagonal stub's fixed reach falls well short of the lane height --
jumping straight from the stub to the lane point was then a genuinely
diagonal segment (not axis-aligned), which sliced through the straight
box's near corner. Fixed by inserting one more point (at the stub's own
x) when the stub doesn't already clear, keeping every segment
axis-aligned; that x is provably always clear of the straight box given
the =xGap >= ARC_DIAGONAL_STUB= gate already in place, so the extra
vertical leg never enters it.

At the user's request, a systematic swept regression test (many
place/transition placements, both arc directions, asserting no crossing
in any of them) was added as a standing guard rather than waiting for
the next one-off report -- and it immediately caught a *fifth* bug of
the same family, this time in the route-around-via-a-west-lane branch
(the one the =xGap= fix falls back to): its clearance margins were each
measured off only the *nearer* box's own edge (=exit.y + MARGIN= for
the bottom lane, =enter.y - MARGIN= for the top lane), which was correct
back when this branch was only reached for a target cleanly above the
source, but broke once it also started covering merely-touching
x-ranges, where the two boxes can overlap substantially in y. Fixed by
measuring both lane heights against *both* boxes
(=Math.max(sourceBottom, targetBottom) + MARGIN= and
=Math.min(sourceBox.y, targetBox.y) - MARGIN=), matching the same
"clear of both, not just the nearer one" principle the diagonal branch
already relies on. The sweep (12,748 checked placements at a finer
10px grid, run standalone) now finds zero crossings.

Extended with two more swept regression tests, per the user's follow-up
ask for "any other sweeping tests" (also raised specifically for block
diagrams): one sweeps place/transition *sizes* as well as positions
(tiny places, very wide/narrow transitions) against =verticalArcPath=,
and one sweeps =orthogonalPath= -- the routing function block-diagram
access/channel edges and ER arcs actually use, which had zero prior test
coverage of any kind. Both came back clean (no crossings found in either
a standalone finer sweep or the in-suite coarser one), so these are
pure standing regression guards, not fixes -- =orthogonalPath= is now
exported (like =verticalArcPath=) purely so the test can call it
directly.

* Milestone C — ER / value-range diagrams

** DONE Create entity sets and (possibly n-ary) relations (primitive)
=EntitySet=/=Relation= element types, palette buttons shown when the
active view's =diagramType= is =er=. Arcs connect them via the same
generic =FmcModel.arcs=/=addArc= mechanism Petri nets use (one bipartite-
pair check per diagram type, not two parallel arc concepts). Role labels
and n-ary relations beyond what the generic arc already allows are still
deferred -- cardinality, reification, and orthogonal partitioning are now
DONE (see below).

An entity set's corner rounding is =min(width, height) / 2= (a stadium/
pill shape on a non-square box, a full circle on a square one) rather
than a plain location's smaller fixed 12px rounding, so it reads visibly
different from an ordinary location box.

** DONE ER cardinality arrows (1:n / n:1 / 1:1)
An entity_set<->relation arc's =cardinality= field (=null= or ='one'=,
toggled via the arc's right-click menu) draws a small filled arrow a bit
inside the relation's own box, pointing further inward -- FMC's "arrow
inside the relation symbol" convention (=spec/index.html='s Cardinality
and roles section), distinct from the main edge's own arrowhead.

** DONE ER independent (orthogonal) partitioning, drawn as a triangle node
Superseded an earlier, incorrect first attempt (a =kind: 'inheritance'=
arc connecting two entity sets directly with a hollow-triangle
*arrowhead*, modeled on UML generalization) after direct feedback that
what FMC/ER partitioning actually calls for is a triangle *node*, not an
arrow decoration: the partitioned (super)set connects to the triangle's
apex, and each part (subset) connects to its base -- see
=spec/index.html='s "Orthogonal partitioning" section, which already
defined the =part= relation formally but had no visual notation for it
yet. =ElementType.PARTITION= is a new node type (rendered as an actual
triangle shape in =buildShape=, apex up); it joins the general
=FmcModel.arcs=/=addArc= bipartite mechanism as a third valid pair
(=entity_set<->partition=, alongside =place<->transition= and
=entity_set<->relation=) -- direction carries the meaning, an
=entity_set->partition= arc is the superset (apex side), a
=partition->entity_set= arc is one part (base side). A partitioning arc
draws as a plain line with no arrowhead (the triangle itself already
carries the meaning) via =drawArc='s new =isPartitionArc= flag. The old
=kind: 'inheritance'= special case, its palette button, and
=ConnectorKind.INHERITANCE= were removed entirely rather than kept
