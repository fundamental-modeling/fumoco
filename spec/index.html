This document specifies the notation of the Fundamental Modeling Concepts (FMC) as implemented by Fumoco, a browser-based visual editor. It defines FMC's core terminology, the three FMC diagram types (block diagrams, Petri nets, and entity-relationship diagrams) as bipartite graphs over that terminology, and the rules that make a diagram of each type well-formed. The block diagram section is normative and matches Fumoco's shipped editor; the Petri net and entity-relationship sections are drafted normatively in advance of their editors being built, so later implementation work has something concrete to conform to rather than improvising semantics while also writing code. An informative appendix summarizes layout guidance that shaped several of Fumoco's editor features.

This is not a W3C specification and is not on the W3C standards track. It is Fumoco's own working specification of FMC notation, written in a W3C-ReSpec-style document because that format gives a free table of contents, section numbering, and a references section for a document that otherwise has no such tooling of its own. It is derived from, and should be read alongside, the FMC Consortium's own reference material at fmc-modeling.org — in particular the Notation Reference, the Metamodel page, and the Visualization Guidelines (see the References section, and spec/SOURCES.md in this repository for the full list of source material screened while writing this document). Where this document and the FMC Consortium's own material disagree, the Consortium's material is authoritative for what FMC *is*; this document only aims to be authoritative for what Fumoco's editor *implements and enforces*.

Introduction

FMC describes a software-intensive system along three largely independent aspects, each with its own diagram type:

Compositional structure
which components a system consists of and how they're connected — drawn as a block diagram.
Dynamic structure
what actually happens over time — the operations components perform and how those operations depend on one another — drawn as a Petri net.
Value range structure
what information is observable at a given point in the system, and how pieces of information relate to each other — drawn as an entity-relationship diagram.

All three diagram types share one property: each is a bipartite graph — its nodes split into exactly two disjoint kinds, and every edge connects a node of one kind to a node of the other kind, never two nodes of the same kind. Which two kinds, and what an edge between them means, differs per diagram type; Terminology and Conformance below fixes the vocabulary shared across all three before each diagram type's own section states its specific bipartite rule.

Terminology and Conformance

This section fixes the core FMC vocabulary that the rest of this document, and Fumoco's data model, builds on.

System components

A system consists of components, split into two kinds:

Agent
An active component. An agent performs operations and, in doing so, is the only kind of component that can access a location. A human agent is an agent that represents a person rather than a technical component; it behaves identically to any other agent and is distinguished only for readability.
Location
A passive component — a place where information can be observed. A location is either a storage or a channel:
  • A storage holds information that persists until an agent changes it again. At least one agent accesses a given storage.
  • A channel carries information that is transient — it exists only for as long as a transmission is in progress. A channel connects at least two agents, since its purpose is communication between them (a storage accessed by more than one agent can also serve this purpose, but a channel is specifically for it).
Both kinds of location can represent either a purely conceptual element of a high-level model, or a concrete technical component (an OS-level task queue, a network connection, a disk).

Agents are conventionally drawn with angular (rectangular) outlines and locations with rounded outlines, regardless of which specific diagram type they appear in — this angular/rounded distinction is what a diagram reader uses to tell the two bipartite node kinds apart at a glance, and Fumoco preserves it (a channel is drawn as a small near-circular location; an ordinary storage as a rounded-corner rectangle).

Access

An agent connects to a location via an access edge of one of three kinds:

Read access
The agent observes the location's current value without changing it.
Write access
The agent replaces the location's value.
Modify access
A read followed by a write to the same location as one unit — the agent needs the current value to compute the new one (an increment is the canonical example).

By convention, read/write access to a storage is drawn as two separate directed edges (one per direction actually used); read/write access to a channel is drawn as a single undirected edge instead, since a channel's smaller size makes two full edges visually heavier than the distinction is worth. Modify access is its own single edge kind regardless of which location it targets.

Containment and structure variance

Any component (agent or location) may be drawn nested inside another component to show a whole-part relationship; nesting is purely a display convention layered on top of the bipartite access structure, not a third node or edge kind of its own. Fumoco treats containment as many-to-many (a component can be nested inside more than one container) rather than assuming a strict tree, and separately tracks whether a given containment relationship is actually displayed nested in a particular view — see Fumoco's own PFLICHTENHEFT.md for that distinction, which is an editor design decision rather than part of FMC notation itself.

Structure variance is the notational convention for showing that the system's own structure — which components exist — can change at runtime: a dashed outline on a location marks it as the place where such a structural change is observed, with the agent responsible for the change drawn with access to it exactly like any other read/write/modify access.

Values

A value is the information observable at a location at a given moment. A value is unstructured (atomic — a bit, a number) or structured (composed of two or more other values — a record, a stack, an entire database's contents). Both a storage's held content and a message currently in transit on a channel are values in this sense. Values are the subject matter of an entity-relationship diagram.

Operations, events, and causal ordering

An operation is the smallest activity an agent performs; it consists of at least one write access (a pure generator writes without reading first) and zero or more read accesses. When a write access actually changes a location's value, that change is an event, occurring at exactly one point in time and carrying a pre-value and a post-value (the value immediately before and after). An event may in turn cause an agent connected to that location to perform an operation of its own. Events are only ever partially ordered — causal dependency, not a single global clock. This dynamic-structure vocabulary is what a Petri net depicts: a place corresponds to where an event/value-change can be observed, a transition to an operation.

Block Diagrams

Normative. Matches Fumoco's Milestone A editor.

A block diagram depicts a system's compositional structure. Its bipartite node kinds are agent (angular; includes human agent) and location (rounded; a storage or a channel). Every edge is an access edge connecting an agent to a location — never agent to agent, never location to location.

Channel notation

A channel is a location like any other for bipartite-rule purposes, but its own read/write access edges carry additional meaning about direction:

  • Unidirectional (directed) channel: one agent has write access, another has read access to the same channel — information flows only from writer to reader. Drawn as an arrow into the channel from the writer and an arrow out of it to the reader.
  • Bidirectional channel: both agents have modify access to the channel — information can flow either way. Drawn as a plain undirected line through the channel, no arrowheads, since neither agent is fixed as sender or receiver.
  • Request/response channel: one agent requests something from another, which then responds — modeled as two unidirectional channels (or, in Fumoco's model, two access edges on one shared channel location) in opposite directions. Because this pattern is extremely common, a shorthand notation exists: a single bold, direction- carrying glyph label (Fumoco uses "R▶") in place of separate request/response arrowheads and separate REQ/RES labels.

Structure variance in a block diagram

Per Containment and structure variance: a dashed-outline location marks where a structural change (an agent or location coming into or going out of existence) is observed, with the responsible agent's access to it drawn as ordinary modify access.

Petri Nets

Normative-in-advance. No Fumoco editor support yet (Milestone B) — this section is what that editor must conform to once built.

An FMC Petri net depicts a system's dynamic structure as a transition/place net. Its bipartite node kinds are transition (angular; an operation, event, or activity) and place (rounded; a control state or condition). Every edge is a directed arc connecting a place to a transition or a transition to a place — never place to place, never transition to transition.

Marking and capacity

A place may be marked — holding one or more tokens. Ordinary places hold at most one token at a time. A multi-token place is drawn enlarged with an explicit capacity annotation (n > 1); a place with unlimited capacity is drawn as a double circle instead. An arc carries a weight (default 1 when unlabeled) specifying how many tokens it consumes or produces when its transition fires.

NOP transitions and swimlanes

A NOP ("no operation") transition performs no action; it exists purely to preserve bipartiteness when a construct would otherwise need two adjacent places or two adjacent transitions. A swimlane divider groups transitions by which agent performs them (the same agent/location vocabulary as a block diagram, projected onto the dynamic-structure view); a transition crossing a swimlane boundary represents communication between the two agents on either side.

Standard constructs

Four control-flow shapes recur often enough to have standard, recognizable layouts (see also Petri Net in the visualization appendix):

Sequence
Transitions fire one after another in a fixed order, with no alternative ordering possible.
Case
Exactly one of several transitions fires, chosen by a condition attached to each candidate arc (an unconditioned fallback arc is conventionally read as "otherwise").
Loop
A transition may fire repeatedly for as long as a condition holds.
Concurrency
Two or more transitions have no ordering constraint between them at all and may fire independently.

Recursion elements

A recursive Petri net uses a dedicated stack place (a capacity-1 or infinite-capacity place holding stack tokens that record a return position) and a return place — an input place shared by at least two transitions that also read from a stack place, resolving the always-present conflict at a return place by consuming the most recently pushed stack token first. Every recursive diagram has exactly one recursion entry point and exactly one transition representing the recursion's base case (the point where it stops calling itself again).

Entity-Relationship Diagrams

Normative-in-advance. No Fumoco editor support yet (Milestone C) — this section is what that editor must conform to once built.

An FMC entity-relationship (ER) diagram depicts a system's value range structure. Its bipartite node kinds are relation (angular) and entity set (rounded, a classified collection of entities). Every edge is an arc connecting an entity set to a relation — never entity set to entity set, never relation to relation. A relation is itself a node (not merely a labeled edge) specifically so that it can be n-ary, connecting more than two entity sets at once, and so that it can itself be the subject of further structure (see Reification below).

Cardinality and roles

An arc between an entity set and a relation may carry a cardinality range (min, max) stating how many times each entity from that set participates in the relation, and a role label clarifying the nature of that participation. A binary relation's common cardinality shapes each have a conventional shorthand: an n:m relation (unrestricted on both sides), a 1:n relation (a function from one side to the other, drawn with an arrow inside the relation symbol instead of spelled-out cardinality ranges), and a 1:1 relation (a bijection, drawn the same way with arrows on both sides). Any cardinality that deviates from what the shorthand implies must still be stated explicitly.

A relation's identifier is aligned either with one of its entity sets (read as "<that entity set> <relation> <other entity set>", conventionally a verb) or centered on the relation symbol itself (no implied reading direction, conventionally a noun).

Reification and orthogonal partitioning

Reification turns the elements of a relation into the elements of a new entity set, which can then participate in further relations of its own — the mechanism by which an ER diagram lets a relationship itself become a first-class subject. Orthogonal partitioning is splitting one entity set into subsets along two (or more) independent classification axes at once, each axis drawn as its own partitioning rather than forcing a single hierarchy. A structure entity lets an entire sub-structure (a set of entity sets and relations) be folded into a single entity set for use one level up — most useful for showing a level and its own meta-level together.

Appendix: Visualization Guidance

This appendix is informative, not normative — it doesn't define what a diagram of a given type *means*, only what tends to make one easier for a human to read. It summarizes the guidance that motivated several already-shipped Fumoco editor features (orthogonal edge routing with rounded corners, grid snap, resize handles) as well as several not-yet-built ones tracked as OPEN items in implementation_plan.org (see that file and LASTENHEFT.md's "Visualization guidance" section for the concrete, actionable list). It groups the general guidance below into two intentions that sometimes pull in opposite directions — a diagram can't always be optimized for both at once, and treating these as advice to weigh rather than hard rules is itself part of the guidance.

Visual perception

Guidance aimed at reducing visual clutter and effort: minimize edge crossings; prefer horizontal/vertical edges over diagonal ones; round edge corners so the eye can follow a bend more naturally; merge edges heading to the same node into a shared trunk near that node; keep edges from running too close to unrelated nodes or to each other; keep node-to-node distances neither so short that a connection reads as trivial nor so long that the reader loses track of it; give nodes of the same kind a consistent size and shape rather than sizing them off how much label text happens to fit; use a placeholder-plus-ellipsis convention to represent a set of similar nodes without drawing every one; keep alignment and spacing consistent across the diagram (harmonization); make a node's line weight visibly different from an edge's so the two are never ambiguous; keep labels horizontal, in a consistent font, short, and unambiguous about which element they belong to; use color sparingly, and prefer muted tones for grouping frames so the grouped content stays the visual focus; and keep the overall diagram at a size appropriate to both its intended audience and a standard sheet of paper or screen.

Stressing semantics

Guidance aimed at using layout itself to communicate meaning beyond the raw notation: place more important nodes centrally and give them comparatively more visual weight; place related nodes near each other, and nodes that belong to the same enclosing frame are read as related even at a distance; use nesting to stress a containment (or containment-like) relationship, since it both communicates the relationship and reduces the edge count needed to state it explicitly; keep a consistent flow direction (top-to-bottom or left-to-right) when a diagram has a natural sequence; give structurally similar groups of nodes visually similar, symmetric layouts so their structural correspondence is obvious at a glance; and preserve a diagram's layout across related diagrams shown at different levels of detail, so a reader moving between levels doesn't have to re-orient from scratch.

Block diagram specific

A channel's read/write access draws as a single undirected edge (see Channel notation) rather than two directed ones, precisely because a channel is drawn small enough that two full edges would look heavier than the distinction is worth. Grouping nodes purely to reduce edge count (rather than to show a real containment relationship) should be drawn with a lighter line weight than an ordinary agent/location, so the two purposes of a frame stay visually distinguishable. When no other flow is implied, place the most important component centrally, following the standard arrangement below rather than an arbitrary one.

Petri Net

The four standard constructs each have a canonical, recognizable layout: a sequence typically omits the place between consecutive transitions to save space; a case uses an edge tree both to attach conditions cleanly and to re-merge the branches symmetrically after the decision; a loop's entry/exit NOP transitions are drawn smaller and unlabeled since they carry no meaning of their own; concurrency is drawn with the splitting/joining transitions sized to visually span every transition they spread across. A standard flow direction (top-to- bottom or left-to-right) should hold consistently across a diagram, with input places above/left and output places below/ right of a transition along that axis — loop constructs, whose input and output place are the same place, are the natural exception. When a Petri net's normal control-flow path would otherwise be visually buried under error-handling branches, the normal path should be kept visually prominent (e.g. a separated, emphasized main line) with error handling set to the side, or folded into a nested sub-diagram rather than inlined at the same level.

Entity-Relationship Diagram specific

A relation node's shape stays rectangular; an entity set's shape may vary (including non-rectangular outlines) the same way a block diagram's location shapes may. An n-ary relation is typically drawn larger than a binary one, both to signal the difference and to give its several arcs room to align cleanly. Label a relation with a verb when its identifier is aligned to one entity set (implying a reading direction) and with a noun when centered (implying none) — see Cardinality and roles.

Named standard layouts

Block diagram: standard arrangement
The system of interest occupies the visual center and most of the diagram's area; its environment (users above, other external components placed by their role — input, output, and so on) surrounds it rather than crowding in from one arbitrary side.
Block diagram: client-server pattern
Clients arranged above, server (and any database) below, in a scheme of "several connect to few" from top to bottom — the same scheme scales from a simple two-tier layout to an n-tier one.
Petri net: saving space in a long net
A folding pattern for a net that would otherwise run very long in its dominant flow direction, still read top-to-bottom and left-to-right within each fold.

Conformance

A diagram conforms to this specification for a given diagram type if it obeys that type's bipartite rule (every edge connects the two designated node kinds and no others) and every construct it uses matches that construct's definition in the corresponding section above. The Visualization Guidance appendix is explicitly non-normative: a diagram that ignores some or all of it is still a conforming FMC diagram, just a harder-to-read one.
